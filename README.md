# Smart Credit Cabinet

## Назначение решения

**Smart Credit Cabinet** — это демонстрационный прототип веб-приложения (MVP), имитирующий цифровой процесс подачи и рассмотрения заявок на кредитование малого и среднего бизнеса. Решение реализует два сценария:

- **Кабинет предпринимателя** — подача заявки в 3 шага, отслеживание статуса, просмотр предварительной оценки риска и пошаговое продвижение заявки (отправка, оформление документов, моделирование выдачи).
- **Рабочее место сотрудника банка** — очередь заявок, просмотр данных, объяснимый скоринг и смена статуса заявки (проверка, рассмотрение, запрос уточнений, одобрение, отказ, альтернативные условия).

**Важно:** это прототип. Он использует синтетические данные, не подключается к кредитным бюро и официальным реестрам.

---

## Архитектура

Приложение — монолитный веб-сервис на **Flask** с серверным рендерингом (Jinja2 через `render_template_string`), хранением данных в **SQLite** и одним внешним HTTP-вызовом (**DaData API** для проверки ИНН).

### Слои:

Представление — единый Jinja2-шаблон TEMPLATE + функция page(), собирающая страницу из каркаса и HTML-фрагмента конкретной view.
Маршрутизация — Flask-эндпоинты трёх групп: публичные (/, /health, выбор роли), клиентские (/customer, /new, /application/<id>), банковские (/bank, /bank/application/<id>). Доступ проверяется по session["role"].
Бизнес-логика — валидация (ИНН, поля, даты, 12 месяцев выручки), внешняя проверка компании через DaData, эвристический скоринг heuristic_v2 (0–100, риск + разбивка по факторам).
Доступ к данным — тонкая обёртка над sqlite3 (connect, init_db, get_app), без ORM.
Данные: SQLite-файл credit.db, одна таблица applications с «жёсткими» колонками и JSON-полем extra_data (орг. форма, дата регистрации, помесячная выручка, детали скоринга).
Состояния заявки: конечный автомат draft → submitted → checking → review → approved → signed → funded с ответвлениями more_info, offer, rejected. Переходы инициирует клиент (submit/sign/fund) или банк (checking/review/more_info/approved/offer/rejected); комментарий пишется в decision.
Внешние зависимости: файл SQLite (DB_PATH) и DaData Suggestions API (единственный синхронный HTTP-вызов, токен DADATA_API_KEY).
Поток запроса: браузер → маршрут Flask → проверка роли → чтение из SQLite → бизнес-логика (валидация/DaData/скоринг) → сборка HTML → page() → ответ. Асинхронности нет.
Клиентский JS: только на /new — мастер из 3 шагов, динамические поля, клиентская проверка ИНН и согласованности прибыли.
Ограничения: нет аутентификации (роль в cookie переключается без пароля), секреты в коде, нет CSRF, нет аудита/логирования, SQLite и встроенный сервер Flask не для продакшена. Всё это — осознанный компромисс ради простоты MVP.


### Ключевые модули (`app.py`)

| Компонент | Назначение |
|---|---|
| `init_db()` / `connect()` / `get_app()` | Инициализация SQLite и доступ к данным. Таблица `applications` + демо-записи (3 заявки). |
| `calculate_score(a)` | Объяснимый скоринг `heuristic_v2` (0–100). Возвращает балл, риск и разбивку по факторам. |
| `validate_company_data()` | Проверка ИНН/названия через DaData (`suggestions.dadata.ru`). |
| `inn_valid()` | Локальная проверка контрольных цифр ИНН (10 и 12 цифр). |
| `TEMPLATE`, `page()` | Базовый HTML-шаблон (стили, шапка, подвал) и функция рендеринга страницы. |
| `refresh_preliminary_scores()` | Пересчёт скоринга для всех записей актуальной версией правил. |

### Маршруты

| Метод | Путь | Роль | Описание |
|---|---|---|---|
| GET | `/` | — | Главная, выбор роли |
| GET | `/role/<customer\|bank>` | — | Установка роли в сессии |
| GET | `/switch` | — | Сброс роли |
| GET | `/customer` | customer | Список заявок клиента |
| GET/POST | `/new` | customer | Мастер из 3 шагов, создание заявки |
| GET/POST | `/application/<id>` | customer | Детали заявки, действия (`submit`, `sign`, `fund`) |
| GET | `/bank` | bank | Очередь заявок |
| GET/POST | `/bank/application/<id>` | bank | Рассмотрение, смена статуса |
| GET | `/health` | — | Проверка живости (`{"status":"ok"}`) |

### Модель данных (таблица `applications`)

`id, company, inn, contact, product, amount, term, purpose, revenue, expenses, debt, overdue, status, score, risk, decision, created_at, updated_at, extra_data`

Поле `extra_data` — JSON с расширенными сведениями (`org_form`, `reg_date`, помесячная выручка, `score_details` и т.д.). Статусы описаны в `STATUSES`.

### Скоринг `heuristic_v2` (0–100)

| Фактор | Макс. балл |
|---|---|
| Рентабельность (маржа) | 15 |
| Покрытие платежей (DSCR) | 25 |
| Стабильность выручки (CV по 12 месяцам) | 20 |
| Текущая долговая нагрузка | 15 |
| Срок работы бизнеса | 5 |
| Размер кредита к выручке | 10 |
| Срок кредитования | 10 |

Риск: `Низкий` ≥ 75, `Средний` ≥ 50, иначе `Высокий`.

## Требования к окружению

- **Python 3.9+**
- Стандартные модули: `sqlite3`, `os`, `re`, `json`, `datetime`
- Внешние пакеты:
  - `flask`
  - `requests`
- Доступ в интернет к `https://suggestions.dadata.ru` (для проверки ИНН)
- Свободный TCP-порт (по умолчанию `8000`)

Flask>=2.0
requests>=2.25

```bash
python -m venv .venv

```


## Используемые компоненты:
Flask — маршрутизация, сессии, flash-сообщения, шаблоны.
Jinja2 (render_template_string) — единый HTML-шаблон со встроенными CSS/JS.
SQLite3 — хранение заявок в одном файле, без внешнего сервера БД.
requests — синхронный HTTP-вызов к DaData Suggestions API (findById/party).
DaData API — получение официального названия, ОКВЭД и статуса компании по ИНН. 
Клиентский JS (в шаблоне /new) — мастер из 3 шагов, динамические поля (цель «Другое», наличие кредитов), проверка согласованности прибыли.

Пошаговый сценарий проверки
### Шаг 1. Запуск и главная
Запустите приложение, откройте /. Убедитесь, что отображаются три карточки сценариев.
### Шаг 2. Кабинет клиента (просмотр демо-данных)
Нажмите «Войти как клиент» (/role/customer).
В списке должны быть 3 демо-заявки со статусами «На рассмотрении», «Нужны уточнения», «Отказ» и разными уровнями риска.
### Шаг 3. Подача новой заявки
Нажмите «＋ Новая заявка».
#### Шаг 1: выберите орг. форму (ИП — 12 цифр ИНН, ООО — 10), введите реальный/тестовый ИНН с корректными контрольными цифрами, заполните название, сферу, дату регистрации (не в будущем), ФИО, роль, телефон, e-mail.
#### Шаг 2: выберите продукт и цель (проверьте, что при «Другое» появляется поле уточнения), сумму, срок.
#### Шаг 3: заполните выручку, расходы, прибыль; раскройте блок 12 месяцев и заполните суммы и годы; укажите наличие действующих кредитов (при «Да» появляется поле платежей). Нажмите «Отправить заявку».
Ожидаемо: flash-сообщение о сохранении, переход на страницу заявки; статус Проверка данных, рассчитан скоринг и отображается разбивка по факторам и ограничения.
#### Шаг 4. Проверка валидации
Попробуйте ИНН неверной длины/с неверными контрольными цифрами — должно появиться сообщение об ошибке.
Укажите дату регистрации в будущем — ошибка.
Оставьте обязательное поле пустым — браузерная/серверная валидация заблокирует отправку.
#### Шаг 5. Обработка заявки в банке
Через «Сменить роль» → «Войти как сотрудник» (/role/bank).
В очереди откройте новую заявку, просмотрите данные и скоринг.
Последовательно меняйте статусы: «Проверка данных завершена» → «Передать на рассмотрение» → «Одобрить (демо)». Убедитесь, что статус и комментарий обновляются.
#### Шаг 6. Завершение сценария клиентом
Вернитесь в кабинет клиента, откройте заявку со статусом «Одобрена».
Нажмите «Оформить документы (демо)» → статус Документы оформлены.
Нажмите «Смоделировать выдачу средств» → статус Финансирование выдано.
#### Шаг 7. Служебные проверки
/health возвращает {"status": "ok", "service": "smart-credit-cabinet"}.
Несуществующий путь/заявка → страница 404 с кнопкой «На главную».
#### Шаг 8 (опционально). Пересчёт скоринга
В интерактивной консоли: from app import refresh_preliminary_scores; refresh_preliminary_scores() — пересчитает баллы для всех записей текущей версией правил.
